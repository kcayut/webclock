## iPad mini 1／iOS 9 操作清單

以下各項目前均待使用者驗收；勾選時應在同列記錄結果與時間。管理頁可在平常使用的管理瀏覽器操作，iPad 負責驗收時鐘顯示與響鈴；另行記錄 iOS 9 是否可操作管理頁，不因現代瀏覽器通過而推定。

- [ ] **啟動與選用功能失敗：**在線開啟 `/`，確認秒數立即前進。再讓 Server 不可達，確認錯誤可關閉、時鐘仍走；不支援的離線／音訊功能不得令整頁無法啟動。
- [ ] **跨日與長時間：**連續顯示至少 24 小時並跨過午夜，記錄起訖與另一可信時間來源的差距，確認日期／星期、提醒輪播、畫面與秒數正常；測試期間保持前景與亮屏。
- [ ] **已載入後斷網：**先完成一次 Server 校時，再斷 Wi-Fi，確認以最後校時基準續走、本機提醒出現；重連後回到伺服器行程且不重複顯示。另測尚未成功校時就離線的啟動，應採裝置時間。
- [ ] **離線重開：**在線時查看離線準備結果；只有顯示準備完成才測離線重新開頁。若不支援或非安全來源，應明確顯示不可用，記錄為能力限制，不能把「已開頁斷網仍走」記為可離線重開。
- [ ] **本機提醒與 Server URL：**新增有／無時間的提醒、重開面板、刪除、重整，確認保存範圍。輸入 Server URL 後保存並重連，確認狀態及重開後的網址；勿清除原有網站資料來測試。
- [ ] **顯示設定：**逐項測夜間開始／恢復、跨午夜、亮度、夜間黑畫面與手動黑畫面優先；切換顯示時區、12／24 小時制及三種語言，實際排程時間不得變動。編輯中切換管理頁淺／深色應保留未送出內容；語言切換如要求確認，取消後輸入仍在。
- [ ] **音訊與視覺：**每次重開頁先按鈴鐺啟用，依次試聽 7 種音色；比較各鬧鐘的 0%、中間值與 100%，靜音仍有紅邊。測穩定紅邊及閃動；兩次分開點擊只停止本頁當次，另一顯示端與排程仍保留。
- [ ] **暫停與恢復：**建一個近期響鈴的固定時間重複鬧鐘，選暫停一次，記錄略過時刻、恢復倒數及下一次響鈴；確認原定時刻不響、過後恢復啟用。另測提前恢復、永久停用、已暫停時不能再略過另一日期。
- [ ] **行程與日期邊界：**在專用測試行事曆建立重複行程，各建「單次」與「整個系列」聯動；改期一次、取消一次，等訂閱更新後看預覽與實際響鈴。隱藏來源仍應聯動；移除／讀取失敗不得變成每日鬧鐘。測全天、跨日及提前響鈴跨日期；工作日／假日判斷依台灣的實際響鈴日期。

## 主機與同步驗收

- [ ] **安裝與自動啟動：**在確認的目標主機以實際部署方式安裝，重啟服務及主機，確認設定／提醒／排程保留、服務自動啟動，記錄主機與服務狀態。
- [ ] **更新及失敗回復：**先保留獨立完整備份；在可回復的測試副本照[使用指南](guide.md#備份資料與更新)升級，確認健康檢查、狀態保存與成功啟動。受控製造更新失敗後確認程式、環境、資料回復；失敗副本／manifest 保留。未跑真實主機時不勾選。
- [ ] **要求同步 → 輪詢 → ACK：**依[API 範例](server-api.md#狀態與同步確認)註冊測試 ID，管理頁要求同步，裝置輪詢取得指令，未 ACK 再輪詢仍是同 ID；同步成功後附 revision 與 ACK，重新載入管理頁確認指令消失。另測斷線、Server 重啟、ACK 重送；只確認契約，不把 ACK 當成實際響鈴證明。

## 2027 年之後的台灣工作日資料

沿用 `webclock/data/taiwan_calendar.json` 與 `HolidayService`，以維護者核對後隨版本發布的方式更新，不加常駐下載器或排程。現有檔案覆蓋 2023-01-01 至 2027-12-31，`source.verified_at` 為 2026-09-23；這是檔案既有來源紀錄，並非本次重新驗證全部年份。

1. 每次準備新年度版本或官方修訂時，從人事行政總處的[政府行政機關辦公日曆表資料集](https://data.gov.tw/dataset/14718)取得該年度正式 CSV，對照核定公告。資料集定義「是否放假」`0` 為上班、`2` 為放假；本次於 2026-10-02 核對來源頁。下載來源若不存在、欄位未知或資料不完整，保留舊資料與原 coverage，不能先拉長範圍。
2. 保存官方 URL、原始檔名、SHA-256、取得／核對日期與修訂依據。依既有 schema 1 更新 `holidays` 的日期與名稱、`makeup_workdays` 的週末上班日；維持 `Asia/Taipei`。週末預設放假，補班清單優先，平日放假必須列入 `holidays`。若使用既有產生工具輔助，仍以官方逐日結果核對，並如實更新 `source.generator`。
3. 確認每個新增年度有完整 365／366 個唯一日期，沒有缺日、重複或無效旗標；用 `HolidayService.get_day_type()` 逐日對照 CSV 的工作／假日結果。核對跨年、閏日、平日假期、補班與已涵蓋年度修訂，將比對摘要和原檔 hash 寫入既有 `source.verification_<year>`，成功後才延伸 `coverage.end` 與 `source.verified_at`。
4. 執行排程／Server API 回歸，確認範圍外的前後日期仍為 `type=unknown`、`known=false`、`holiday=null`。依賴假日的規則不得回退成「週一至週五」猜測；未使用假日條件的普通排程維持原有計算方式。
5. 透過正常版本更新部署並重啟 Server（服務啟動時讀取資料檔），確認 `/api/v1/device/holidays` 的來源、coverage、`holiday_revision` 與 ETag 已反映新版，裝置完成下一次下載／ACK。更新失敗使用已有更新器回復流程；離線裝置的舊 coverage 仍保持 `unknown` 邊界。
