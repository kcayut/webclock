# WebClock 日本語ガイド

## 管理者ログインと B0–B3 のテスト範囲

既存インストールは自用モードを維持します。帳密モードは隔離テストのみです。テストサービスを停止し、サービス用ユーザーで `./venv/bin/python scripts/manage_auth.py --state-dir /path/to/test-state setup --username admin --enable-managed-test` を実行して 12 文字以上のパスワードを対話入力し、再起動後に HTTPS の `/admin` へアクセスします。同じ state パスで `reset-password` を使うと全管理 session が失効します。有効期限は最大 8 時間で、管理画面からログアウトできます。B2 の端末参加と B3 の受管表示・グループ画面は実装済みです。本番環境のモード移行と端末のライフサイクル操作は B4 の対象です。

未参加の時計は時刻・日付を表示しますが、非公開の予定・アラームは取得しません。管理 session は端末認証を代替せず、参加コードは管理ログインには使えません。保存と認証の境界は [B0–B1 契約](b0-b1-contract.md)、現行 endpoint は[端末 API](server-api_jp.md)を参照してください。

ホスト全体のバックアップは認証情報を含み、暗号化されません。履歴復元は session・招待の秘密を更新し、session・試行を削除、招待を終了、端末認証情報を失効させます。グループ・内容・観察記録は残ります。旧バックアップによる managed から無認証への降格は禁止です。更新直後の rollback は最新認証状態を保持し、旧コードが対応しなければ停止を維持します。管理画面 version 1 の出力は従来どおり設定とメモだけです。

### グループ設定と端末参加

1. `/schedules#devices` でグループを作成します。既存の表示設定と内容選択を移す場合は、既定グループの初期化を明示的に確認します。新規グループの内容選択は空です。
2. 表示項目ごとに継承または個別設定を選び、既存カレンダー・文字リマインダー・アラームを選択して保存します。明示的な `false`、明るさ `0`、空の内容選択も維持されます。アラームは表示タイムゾーンと独立して台湾時間で計算します。
3. 6 文字の参加コードを生成します。有効期間は 10 分、参加枠は既定 5 台、指定範囲は 1–100 台です。期限と残り枠を表示し、平文コードは生成直後だけ表示します。グループ切替や再読込でコードは失効しませんが、再表示するには再生成が必要です。招待の終了・再生成は参加済み端末を変更しません。
4. 対象ブラウザーで同じサーバーの `/` を開き、「表示グループに参加」を押します。Cookie の確認後にコードを入力すると、独立した端末認証を取得してグループ設定を適用します。公開 Pages や別オリジンの時計からは参加できません。

定期更新、グループ・言語切替、低速保存、読み込み失敗時も、同じページ内の下書きと入力位置を保ちます。ページ全体の再読込では未送信の下書きやコードを保存しません。メンバーの認証状態と最終観察は別に表示し、未報告の値は不明のままです。個別メンバーの移動・無効化・失効操作は B4 の対象で、メンバーがあるグループは削除できません。

参加済みの時計は所属グループの設定と内容だけを取得します。短い通信断では、その実行中に取得した非公開データを最長 5 分の認可期限まで使用できます。認可失敗の確認または期限切れで非公開予定・待機アラームを消去し、現在のブラウザー発音を停止します。時刻・日付とブラウザー内リマインダーは利用できます。オフライン再起動や背景・ロック画面での発音を保証するものではありません。初代 iPad mini／iOS 9 と ESP ファームウェアの新しい認証フローは別途検収が必要です。

## 公開時計

[WebClock 公開時計](https://kcayut.github.io/webclock/)を開くだけで利用できます。アカウントやサーバーは不要です。時刻とタイムゾーンは端末の設定に従い、日付と曜日は繁体字中国語で表示します。横向きでの利用がおすすめです。iPad の Safari では「共有 → ホーム画面に追加」で入口を作れます。

WebClock は初代 iPad mini をきっかけに作られ、古いタブレットでも時刻を安定して表示できるシンプルな時計ページを優先しています。常時表示する場合は、端末側で自動ロックと画面の明るさを調整してください。

オフラインキャッシュ対応ブラウザーでは、最初に接続した状態で開き、接続パネルにオフライン利用の準備完了が表示されるまで待ってください。古い Safari がオフラインでの再起動に対応しない場合でも、オンラインで読み込んだページは切断後も計時を続けます。サイトデータやキャッシュを削除した場合は、再度オンラインで準備が必要です。

## セルフホスト

セルフホスト版には次の入口があります。

- `/`：時計ページ。
- `/admin`：表示設定、カレンダー、文字リマインダー、バックアップと復元。
- `/schedules`：ブラウザーアラームと端末同期状態。

Docker の既定ホストポートは `80`、Linux インストーラーと手動実行は `5000` です。コマンドは [README のクイックインストール](../README_jp.md#クイックインストール)を参照してください。基本的な `.env` 設定は次のとおりです。

```env
PORT=5000
HOST=0.0.0.0
WEBCLOCK_LANGUAGE=ja
```

`WEBCLOCK_LANGUAGE` は初回の表示言語で、`zh-TW`、`en`、`ja` を指定できます。管理サイドバーの言語切替は現在のブラウザー session の管理画面だけに適用し、下書きを維持して時計を変更しません。`/admin` の「共通の表示言語」は共通設定として `webclock_state/settings.json` に保存され、デプロイ時の既定値より優先されます。グループごとに継承または個別の表示言語を選択できます。

管理サイドバーの「表示テーマ」で太陽（ライト）／月（ダーク）のアイコンを選べます。選択中のアイコンが強調表示されます。初期値はライトで、左側ナビと右側の内容に同じ配色を使います。選択は現在のブラウザー・同じオリジンの `localStorage` に保存され、`/admin` と `/schedules` で共有し、開き直しても維持します。大時計や Server の表示設定は変わりません。配色切替でページは再読込されず、未送信の入力を保ちます。

カレンダー URL は `.env` ではなく管理画面で入力します。既存環境の `ICAL_URL` は、管理画面で新しいカレンダー参照元を初めて保存するまで利用できます。

## カレンダーと文字リマインダー

`/admin` の「カレンダー・リマインダー」で「カレンダー参照元設定」を開き、Google、Apple iCloud、その他の ICS 参照元に名前を付けて追加できます。複数の参照元に対応しています。URL は目のボタンを押すまで隠され、保存後は再び隠れます。

参照元設定と時計への表示選択は別々に保存します。参照元を非表示にしても URL は削除されず、アラームの参照元選択にも影響しません。URL は `webclock_state/calendar.json` に保存され、公開時計、状態 API、管理画面からダウンロードした JSON バックアップには含まれません。このファイルや非公開 URL を公開リポジトリにコミットしないでください。

### Apple iCloud

1. [iCloud カレンダー](https://www.icloud.com/calendar/)を開いてサインインします。
2. カレンダーの情報ボタンを開き、「公開カレンダー」を有効にしてリンクをコピーします。
3. `webcal://` または HTTPS のリンクを WebClock に貼り付けて保存します。

WebClock は読み取り専用で約 5 分ごとに更新します。Apple の認証情報は不要で、Apple「リマインダー」App は同期しません。公開リンクを知っている人は誰でもカレンダーを読めるため、時計専用のカレンダーを作り、不要になったら公開共有を停止してください。画面上で URL を隠してもアクセス権は変わりません。

### 文字リマインダー

手動リマインダーには日時、または毎日／毎週の表示時間帯を設定できます。曜日を選ばない場合は毎日です。日付をまたぐ時間帯は開始日の曜日に属します。開始と終了は同じ時刻にできません。両方を空にすると時間帯を解除できます。範囲は開始を含み、終了を含まず、管理画面のタイムゾーンを使います。

期限切れのリマインダーは削除されず、非表示になります。一時停止すると内容を保持したまま表示を止め、後から再開できます。サーバーと短時間切断しても、読み込み済み時計は保存済みの表示設定とブラウザー内リマインダーで動作し、カレンダーとサーバー側リマインダーは再接続後に戻ります。

### ブラウザー内リマインダーと接続パネル

時計の左下にある接続状態ボタンから接続パネルを開き、文字と任意の時刻を入力して追加・削除できます。現在のサイトとブラウザーの `localStorage` に保存され、Server に接続できないときに表示されます。時刻は表示用で、発音せず、時刻を過ぎても自動で消えません。新規項目には日付がなく、削除するまで残ります。編集は削除して再追加します。

ブラウザー内リマインダーはアップロード・端末間同期されず、Server のバックアップにも含まれません。サイトデータを消去すると失われます。`/admin` の Server 側「ローカルリマインダー」参照元とは別で、連動アラームには使えません。再接続すると時計は Server の予定とリマインダーを表示し、ブラウザー内の項目はパネルに残ります。

同じパネルで Server URL を保存し、「今すぐ再接続」で接続を確認できます。保存だけでは接続成功を示さないため、状態表示を確認してください。別のオリジンで時計を開くと保存領域も変わります。リマインダーの保存とオフラインでの再起動は別の機能で、後者には下記のキャッシュ条件が必要です。

## カレンダー連動アラーム

アラームごとに、`/admin` の Server 側ローカルリマインダーを含む 1 つ以上のカレンダー参照元を選べます。

- **予定時刻にアラーム：**時刻付き予定の 0–1440 分前に発生します。終日予定は対象外です。
- **その日に予定があればアラーム：**選択した参照元のいずれかに当日の予定があれば、アラームの固定時刻に発生します。終日・複数日の予定も含みます。

アラームの参照元選択と時計の表示選択は独立しています。曜日、指定日、台湾の休日条件は引き続き適用され、実際のアラーム日の台湾日付で判定します。参照元の取得に失敗した場合や削除された場合、その参照元からはアラームを作らず、他の読み取れる参照元は継続して利用します。

参照元を選んだ後、特定の予定を指定でき、繰り返し予定では「今回のみ」か「シリーズ全体」を選べます。未指定なら選択した参照元の全予定を対象にします。今回のみの連動は元の予定識別子を維持して変更後の日時に追従し、取り消し後に別の予定へ切り替わりません。シリーズ指定はそのシリーズの各回に追従します。購読の更新には最大約 5 分かかるため、更新後に次回のプレビューを確認してください。

## iPad のブラウザーアラーム

1. `/schedules` で時刻と曜日または日付を選びます。「毎日」は全曜日を選択すると消え、どれかを解除すると再表示されます。ベル・ビープ・電子音・チャイム・メロディー・連続ビープ・ソナー・無音から選べます。音量はアラームごとに 0–100%（初期値 100%）で設定でき、試聴にも適用されます。0% は画面表示のみです。
2. 毎日・曜日・指定日のルールでは台湾の休日をスキップできます。振替出勤日は勤務日です。「休日のみ」と「休日をスキップ」は併用できません。
3. iPad の時計ページでベルをタップし、短い確認音を聞いて音声を有効にします。再読み込みや再起動のたびに必要です。
4. アラーム発生時に 2 回タップすると、現在のページの今回分だけを停止します。予定や他の端末には影響しません。

Safari を前面に表示して画面を点灯し、音量と消音設定を確認してください。iOS は画面ロック、App 切り替え、タブ切り替え後に Web 音声やタイマーを中断することがあるため、バックグラウンドやロック中のアラームは保証されません。無音アラームでも赤い枠の通知は表示します。

時計ページは各アラームの次回時刻を約 15 秒ごとに更新します。短い切断中は読み込み済みの次回分を実行できますが、ページの開き直しやそれ以降の予定取得には接続が必要です。60 秒を超えて遅れたアラームは再生しません。休日データの対象外の日付は推測せず、不明のまま扱います。

## 次の予定・一時停止・再開

`/schedules` の概要には次のアラームを表示し、追加・編集画面には現在の台湾時刻、次回時刻、残り時間を表示します。大時計の予定・リマインダー欄は文字の順次表示で、予定のカウントダウンはありません。プレビューや残り時間は実行・発音の成功を証明しません。

固定時刻の繰り返しアラームをオフにすると、1 回だけの一時停止か無期限の無効化を選べます。1 回だけ停止するとスキップ時刻と再開までの残り時間を表示します。その時刻を過ぎると有効表示に戻り、次回は元の規則で計算します。停止中にオンにすれば早めに再開でき、無期限の無効化は手動でオンにする必要があります。日付指定・カレンダー連動では編集画面の「次回をスキップ」を使えます。未来のスキップが残っている間は別の日付を重ねてスキップできません。

## 端末同期状態

`/schedules#devices` には端末 API で登録した端末を表示します。カードには表示名、自報名、種類、登録・最終報告時刻、ファームウェアと revision、能力とその報告時刻が表示されます。管理名は空白のみ不可、100 文字以下で保存でき、再登録や状態報告では上書きしません。現在、管理名の消去には対応していません。未報告情報は「不明」で、能力が非対応となるのは端末が `false` を報告した場合です。これらは実機検証結果ではありません。

「同期を要求」は Server に指令を登録するだけです。端末が状態報告でポーリングして `sync` を受け取り、取得・検証・保存後に ACK を返します。画面は未要求、確認待ち、端末確認済み、確認タイムアウトを区別し、要求・確認時刻を表示します。300 秒間 ACK がなければタイムアウトになりますが、指令は残り、遅れて到着した一致する ACK でも確認できます。再要求は同じ指令と最初の要求時刻を維持し、オフライン端末では直ちに完了しません。

一覧の更新に失敗すると最後に取得した情報を維持し、未更新と表示します。15 秒ごとの一覧自動更新やページ内の言語切り替えでは未保存の名前、入力フォーカス、選択範囲を保持します。ページ全体の再読み込みや開き直しでは草稿を保持しません。`online` は 120 秒以内の報告を示すだけで、ACK や revision の報告も発音・画面更新成功の証明ではありません。[端末 API](server-api_jp.md#状態と指令確認)を参照してください。

観察一覧には 2 種類の端末が含まれます。旧 self 端末は自報 ID と共通の `DEVICE_API_TOKEN` を使用し、コードで参加した schema 3 端末は個別の認証情報を使用します。後者では Server が端末と所属グループを決定して状態を記録します。現在のメンバー認可はグループ画面で確認し、旧観察記録から推測しないでください。時計を開くだけでは自動参加しません。個別端末の移動・無効化・失効操作は B4 の対象です。

## ナイトモードとオフライン利用

「表示設定 → 時刻形式」で 24 時間制または 12 時間制（午前／午後）を選べます。時計、アラーム、カレンダーのリマインダー、ナイトモードの時刻表示と入力に共通で適用されます。初期設定は 24 時間制です。形式を切り替えても、設定済みの実際の時刻は変わりません。

自動ナイトモードでは、毎日の開始時刻、復帰時刻、夜間の明るさ、または黒画面を設定できます。変更するのは Web ページだけで、端末のバックライトや自動ロックは変えません。手動の黒画面が優先されます。

時計ページは接続、アラーム、オフラインキャッシュより先に基本の時刻・日付・曜日を表示します。読み込み済みで前面実行中のページは、通信失敗、API の拒否、追加機能のエラーがあっても計時を続けます。ブラウザー保存領域が使えなくても基本時計は起動します。壊れたブラウザー／API の表示設定は一括で無視し、最後の有効設定、初回は初期値を使います。Server URL の変更や手動再接続後、以前の接続から遅れて届く応答は現在の状態を上書きしません。

接続やオフラインキャッシュの説明は、手動で開く接続パネル内に表示します。通信・キャッシュの失敗で時計上に警告を出したり、パネルを自動で開いたりしません。明示的に指定した明るさ 0、手動黒画面、夜間黒画面は有効なままで、内部の時刻は更新を続けます。OS によるブラウザー停止、画面ロック、ページ未読込時の実行を保証するものではありません。

セルフホスト時計をオフラインで開き直すには、HTTPS または localhost と対応ブラウザーが必要です。通常の `http://LAN_IP` ではオフラインキャッシュを準備できませんが、読み込み済みページは計時を続けられます。キャッシュするのは時計ページと表示用ファイルだけで、管理画面、API、非公開カレンダー、サーバー側リマインダーは含みません。

## バックアップ、データ、更新

管理画面から JSON バックアップを保存・読み込みできます。検証と確認後、サーバーの表示設定と手動リマインダーを置き換えます。上限は 1 MiB、1,000 件、1 件あたり 1,000 文字です。読み込み前のデータは `webclock_state/before-import.json` に保存され、読み込みごとに更新されます。

管理画面の version 1 JSON バックアップは、従来どおり設定と手動リマインダーのみを含みます。スマートスケジュール、端末、非公開カレンダー URL、`.env`、ブラウザー内リマインダーは含まず、既存の読み込みと `before-import.json` の動作は変更しません。

### ホスト側の完全データバックアップと復元

Linux／macOS では、WebClock の依存パッケージをインストール済みの Python で `scripts/backup_clock.py` を実行できます。現在の単一データ領域にある `.env`、旧 `manual_notes.json`、標準・カスタム状態ディレクトリ、カスタムリマインダーファイルを保存し、その中のスマートスケジュール、端末、`calendar.json` も含みます。ソースコード、venv、実行時の環境変数による上書き、systemd unit、Docker 設定、ブラウザーの localStorage は含みません。ホスト移行時は別途保存し、対応するバージョンのプログラムと依存パッケージを用意してください。

**作成・復元の前に、データを書き込むすべてのサービス、コンテナー、その他のプロセスを停止してください。** `--stopped` は操作者による確認であり、ツールがサービスを停止・起動するわけではありません。以下はインストール先で実行します。データを読み書きできるアカウントを使い、元の所有者を維持するために必要なら管理者権限を使用してください。バックアップ先と復元前コピーのディレクトリは毎回新規とし、データパスと重複させないでください。

```bash
mkdir -p -m 700 "$HOME/private-webclock-backups"
venv/bin/python scripts/backup_clock.py create "$HOME/private-webclock-backups/backup-001" --project "$PWD" --stopped
venv/bin/python scripts/backup_clock.py verify "$HOME/private-webclock-backups/backup-001"
```

復元が必要な場合は、すべての書き込みプロセスが停止していることを確認してから実行します。

```bash
venv/bin/python scripts/backup_clock.py restore "$HOME/private-webclock-backups/backup-001" --project "$PWD" --stopped --yes --rollback-dir "$HOME/private-webclock-backups/before-restore-001"
```

`create` は権限 `700` のバックアップディレクトリと `600` の `manifest.json` を作成し、保存後に SHA-256 でファイルを検証します。`verify` はバックアップだけを確認するため、停止は不要です。**バックアップは暗号化されず、非公開 URL や認証情報を含みます。** プロジェクト外の非公開ディレクトリに保存し、アクセスを制限してください。プロジェクト内で Git の除外対象となるのは `.webclock-backup*` の名前だけで、任意のバックアップディレクトリは自動では除外されません。シンボリックリンクと特殊ファイルには対応しません。

復元先のデータパスは、復元先ホストの有効な環境変数、`.env`、明示した `--state-dir /復元先/state --notes-file /復元先/reminders.json` だけから選択し、元ホストの保存パスは使用しません。サービスの環境変数でパスを上書きする場合は、`create` と `restore` に実際のパスを指定してください。カスタムパスを使ったバックアップは、対応する復元先でも同じ包含関係とデータルート内の相対パスを維持する必要があります。バックアップに `.env` が存在し、復元先のデータパスが異なる場合だけ、その中の `WEBCLOCK_STATE_DIR`／`NOTES_FILE` を調整し、他の設定は維持します。元環境に `.env` がなく実行時の環境変数だけを使っていた場合は、起動前にその環境を別途設定してください。Docker では先にコンテナーを停止し、依存パッケージを導入済みのホスト側 Python から実行してください。コンテナー内の `/app/...` ではなくホストのマウント先パスを指定し、Docker volume の場合は実際のホスト上のデータ位置を先に確認します。

`restore` には `--yes` と新規の `--rollback-dir` が必要です。復元前の完全なコピーを残してから対象データを置き換え、通常の内容はバックアップに存在しなければ削除されますが、認証 marker・秘密・認証情報には前述の保護復元規則を適用し、保護モードは下げません。失敗時は回復を試みますが、停電後に自動では再開しません。回復が不完全ならサービスを停止したまま、復元前コピーと `.webclock-restore-*` の作業データを保持してください。コピーでは元の数値 UID／GID を保持します。管理者権限で別ホストや外部ディレクトリに復元した場合は、サービス用アカウントが親ディレクトリを通過でき、データを読み書きできることを確認してください。成功後はデータ、パス、権限を確認してから手動でサービスを起動します。これは Raspberry Pi、Docker、iPad の実機検収完了を意味しません。

### プログラムの更新

新しいソースを取得した後、Docker は次のコマンドで再構築します。

```bash
docker compose up -d --build
```

Linux インストーラーで作成したサービスは次を実行します。

```bash
sudo bash update_clock.sh
```

更新には変更のない Git ワークツリーと fast-forward が必要です。サービスを停止する前にデータパスを検証し、Python 環境と状態データをバックアップします。失敗時は復元を試みます。完全に復元できない場合は、`.webclock-update-*` とその中の `manifest.json`、`failed-data/`、`failed-venv/` を残してください。更新中は管理画面のデータを編集しないでください。また、ローカルテストは Raspberry Pi 実機への導入確認ではありません。

旧更新プログラムから初めて移行する場合は、旧サービスを動かしたまま、`origin/main` を追跡するインストール先で次を実行します。

```bash
git fetch origin
updater_file="$(mktemp /tmp/webclock-updater.XXXXXX)"
git show origin/main:update_clock.py > "$updater_file" &&
    sudo python3 "$updater_file" "$PWD"
```

この入口は新しい更新プログラムを読み込み、検証とバックアップの完了後にだけソースを切り替えます。先に旧更新スクリプト、`git pull`、または上書きインストールを実行しないでください。非 Git 環境では上書きしたソースを自動復元できず、停電後の自動復旧も保証されません。
